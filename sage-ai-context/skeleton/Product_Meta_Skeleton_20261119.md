# Product Meta Skeleton

Skeleton: Product Meta Skeleton
Skeleton version: 1
Skeleton date: 11/19/2026

A Skeleton is a starting file with the structure and the rules in place and blanks for the Product Owner's content. Sage_AI reads this file from the clone of the sage-ai repository, copies it, fills it in with the owner, and writes the result as a dated Markdown file in the owner's Product Meta folder, named with the product shortcode, as in MPX_Product_Meta_YYYYMMDD.md. It does not write to this file.

How to fill it. Replace every bracketed variable. Fill each bucket in the Product Summary when the information exists. Where a bucket is empty, leave a short note that says why. Leave the pin lines bracketed until the folders exist. Set the Version Date to the date of the new file. Where the owner has no overrides or localization, keep the line None yet.

Write the file from the line Document Information below. Leave these notes out of it.

# Document Purpose

This document gives team members, and especially Sage_AI, the brief they need to perform their role. It helps the product owner complete Growth Factors and reach product success.

The product summary in this document is a summary. It is not a source. It is a warm start. It carries what a session needs to begin without fetching a document first.

Where the product summary and a live document disagree, the live document wins and the summary is corrected. The overrides are different. They are rules and not summaries, and they win over the system instructions.

It names key documents, meaning what to read for what. It is not a table of contents and it does not claim to be complete. The project_registry owns the full set.

Open Decisions is the one buffer it owns. Those items are few and short lived. An item moves out of it as soon as a real document exists to hold it.

This document is a dated file in the Product Meta folder in Drive. It is revised in every phase and updated often, and each version is a new dated file. The latest date in the name is live. It holds a bucket for everything a robust Product Meta needs. Fill each bucket when the information exists. When a bucket is empty, leave a short note that says why, for example not yet defined, or does not apply to this product. An empty section should never leave the reader guessing.

## Do Not Use

[List terms, names, or styles that must never appear. Give the reason or the correct replacement.]

- [term or style]: [reason or replacement]

- Requirement and Required Project. Both are retired. Use Growth Factor for one of the thirty-seven, and Project for the unit of work in ProductSage.

- Document Registry as the name of the thing that resolves a Project to its document. It is the Project Registry, a JSON file with two arrays.

- Wrap-up as the name of a mission. It is a Mission Transition.

- Block, or Sprint, as the broad container of a plan. The broad container is a Wave. A Sprint is a named piece of work inside a Wave.

- Em dashes and horizontal rules in documents. En dashes are allowed. This is the house documentation style.

## Standing Instructions

The M-PaX System is the operating system for developing this product into a high-value product. Use it as context for every mission. The project_registry defines project numbers and names. Adhere to that naming scheme. Do not create new names or modify existing ones.

Project numbering is a specific standard. Always use the numbering defined by the project documentation filename. Reference projects by the short form 'XXX X.0.3' or the long form 'XXX X.0.3 MF - Stakeholders', where XXX is the product code and X is the product number. Do not invent versions of project names.

Documents live in Google Drive and are read there by file ID. The registry folder ID, the registry file name pattern, and the PHF root folder ID are under Pins. The project_registry array in the latest dated '[product_shortcode]_Project_Registry_YYYYMMDD.json' resolves every Project to its document. It is built as a whole array and is rarely edited row by row. ProductSage can generate it. The project_meta array in the same file holds child documents, data Sheets, data files, and folders, and is built by scanning the PHF. The rules for reading, for establishing an ID that does not exist yet, and for carrying task state as text are all in the system instructions and are not repeated here.

This document is the living context for all development missions on this product. Update the Version Date with each new dated file.

Editing rule. Revise the Sheet first. Then open each document listed below, place the cursor in the linked table, and choose Update from the table's menu. A document whose table is not updated keeps showing the old values with no warning that it is stale.
